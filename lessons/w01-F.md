# Browser internals: rendering pipeline & critical rendering path

> Đọc ~45 phút. Mục tiêu: giải thích được "từ HTML tới pixel" và biết vì sao `transform` mượt hơn `left`.

## 1. Bức tranh tổng thể

Từ lúc nhận byte HTML đến lúc thấy pixel, trình duyệt đi qua một **pipeline**:

```
HTML bytes → DOM ─┐
                  ├→ Render tree → Layout → Paint → Composite → Màn hình
CSS bytes  → CSSOM┘
```

| Bước | Làm gì | Tên khác |
|---|---|---|
| Parse HTML | Byte → token → node → **DOM** | |
| Parse CSS | Byte → rule → **CSSOM** | |
| Render tree | Gộp DOM + CSSOM, chỉ giữ node **hiển thị**, kèm style đã tính | |
| Layout | Tính vị trí + kích thước từng box | **reflow** |
| Paint | Chuyển box thành lệnh vẽ (màu, chữ, viền, bóng) trên các layer | **repaint** |
| Composite | GPU ghép các layer theo thứ tự đúng | |

Chuỗi các bước này mà trình duyệt phải làm trước khi vẽ được frame đầu tiên gọi là **critical rendering path (CRP)**. Tối ưu CRP = rút ngắn thời gian tới first paint.

## 2. DOM và CSSOM

- HTML parser chạy **tăng dần (incremental)**: nhận được đến đâu parse đến đó, nên có thể vẽ trang khi HTML chưa tải xong.
- CSS thì **không** tăng dần theo nghĩa vẽ được: style cuối file có thể ghi đè style đầu file, nên trình duyệt phải có **toàn bộ CSSOM** trước khi vẽ. Vì vậy:

> **CSS là render-blocking**: chưa có CSSOM thì chưa có render tree, chưa vẽ gì.

- `display: none` → **không** vào render tree (không tốn layout/paint). `visibility: hidden` → **vẫn** vào render tree, vẫn chiếm chỗ.
- `<head>` chứa `<link rel="stylesheet">` đặt sớm là đúng; CSS không cần cho first paint (print, modal hiếm dùng) có thể tách ra bằng `media="print"` hoặc tải muộn.

## 3. JavaScript và parser

Khi gặp `<script src="a.js">` thường (không `async`/`defer`), parser **dừng lại**, tải và chạy script, rồi mới parse tiếp. Lý do: script có thể gọi `document.write` hoặc đọc/sửa DOM.

Hơn nữa script có thể đọc style (`getComputedStyle`), nên trình duyệt phải **chờ CSS đang tải xong** trước khi chạy script. Chuỗi phụ thuộc:

```
CSS tải xong → script chạy được → parser đi tiếp → DOM đủ → render
```

| Cách tải | Tải | Chạy khi nào | Thứ tự | Dùng khi |
|---|---|---|---|---|
| `<script>` | chặn parser | ngay | theo thứ tự | hầu như không nên (trừ inline nhỏ) |
| `async` | song song | **ngay khi tải xong** (có thể chặn parser lúc chạy) | không đảm bảo | script độc lập: analytics, quảng cáo |
| `defer` | song song | **sau khi parse xong HTML**, trước `DOMContentLoaded` | đúng thứ tự | script app phụ thuộc DOM |
| `type="module"` | song song | như `defer` mặc định | theo dependency graph | code hiện đại |

Hai sự kiện hay nhầm:
- `DOMContentLoaded`: DOM đã parse xong (chưa chờ ảnh, CSS không chặn nếu không có script đứng sau).
- `load`: mọi tài nguyên (ảnh, iframe...) tải xong.

## 4. Layout (reflow)

Layout tính **hình học**: rộng/cao/vị trí của mỗi box dựa trên viewport, box model, `display`, `position`...

- Layout thường chạy từ trên xuống nhưng một thay đổi có thể kéo theo cả cây (đổi `width` của cha → con tính lại).
- **Reflow bị kích hoạt khi**: thay đổi kích thước/vị trí, thêm/xoá node, đổi font, resize cửa sổ, thay đổi nội dung chữ...
- **Layout thrashing**: xen kẽ *ghi* style và *đọc* thuộc tính hình học trong vòng lặp, buộc trình duyệt reflow đồng bộ nhiều lần.

```js
// Tệ: mỗi vòng lặp đọc offsetWidth sau khi vừa ghi → forced reflow
for (const el of items) {
  el.style.width = el.parentNode.offsetWidth / 2 + 'px';
}

// Tốt: gom đọc trước, ghi sau
const w = items[0].parentNode.offsetWidth / 2;
for (const el of items) el.style.width = w + 'px';
```

Các thuộc tính "đọc là buộc layout": `offsetWidth/Height`, `clientWidth`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle(...).width`...

## 5. Paint và Composite

- **Paint**: tạo danh sách lệnh vẽ (display list) rồi raster thành pixel, theo từng **layer**.
- **Composite**: GPU ghép các layer. Chỉ thay đổi ở bước này là **rẻ nhất**, không chạy lại layout/paint, thường chạy trên thread riêng (compositor thread) nên mượt cả khi main thread bận.
- Phần tử được đưa lên layer riêng khi có: `transform` 3D / `will-change: transform`, `<video>`, `<canvas>`, `position: fixed` (tuỳ trình duyệt)...

Mức độ "đắt" của thuộc tính CSS khi thay đổi:

| Đổi thuộc tính | Chạy lại | Chi phí |
|---|---|---|
| `width`, `height`, `top/left`, `margin`, `font-size` | Layout → Paint → Composite | cao |
| `color`, `background`, `box-shadow`, `border-radius` | Paint → Composite | vừa |
| `transform`, `opacity` | chỉ Composite | thấp |

→ Animation nên dùng `transform` và `opacity`. Tra từng thuộc tính tại csstriggers.com.

`will-change` chỉ dùng cho phần tử **sắp** animate và bỏ đi sau đó; lạm dụng làm tốn RAM GPU.

## 6. Từ góc nhìn "Core Web Vitals"

| Chỉ số | Đo gì | Liên quan CRP |
|---|---|---|
| **FCP** (First Contentful Paint) | Thời điểm vẽ nội dung đầu tiên | CSS/JS chặn render làm FCP chậm |
| **LCP** (Largest Contentful Paint) | Phần tử lớn nhất hiển thị | ảnh hero, font, CSS chặn |
| **CLS** (Cumulative Layout Shift) | Mức nhảy layout | ảnh không có `width/height`, nội dung chèn muộn |
| **INP** (Interaction to Next Paint) | Độ trễ phản hồi tương tác | main thread bận bởi JS dài |

## 7. Checklist tối ưu CRP

1. Giảm số byte critical: minify, nén (gzip/brotli).
2. Giảm số tài nguyên chặn: inline CSS tối thiểu cho above-the-fold, `defer` cho script.
3. Đặt CSS trong `<head>`, script cuối `<body>` hoặc dùng `defer`.
4. `<link rel="preload">` cho tài nguyên quan trọng (font, hero image); `preconnect` cho origin bên thứ ba.
5. Khai báo `width`/`height` cho ảnh để tránh CLS.
6. Animation dùng `transform`/`opacity`; tránh đọc/ghi layout xen kẽ.
7. Chia nhỏ JS dài (long task > 50ms) để main thread còn phản hồi.
