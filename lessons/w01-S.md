# Network Fundamentals: TCP/IP, DNS, HTTP, TLS

## 1. Bức tranh tổng thể

Khi bạn gõ một URL vào trình duyệt, một chuỗi sự kiện phức tạp diễn ra trong vài trăm mili giây. Hiểu được luồng đi này là nền tảng để debug network, tối ưu performance, và trả lời phỏng vấn system design.

**Mental model: Hành trình của một request**

```
Browser → DNS Resolver → TCP Handshake → TLS Handshake → HTTP Request
   ↑                                                             ↓
   └─────────────────────── HTTP Response ←─────────────────────┘
```

| Layer (OSI) | Protocol | Vai trò | Ví dụ |
|-------------|----------|---------|-------|
| Application | HTTP, DNS | Định dạng dữ liệu, ngữ nghĩa | GET /index.html |
| Transport | TCP, UDP | Kết nối tin cậy, port | Handshake 3 bước |
| Network | IP | Định tuyến gói tin | 192.168.1.1 |
| Link | Ethernet, Wi-Fi | Truyền frame vật lý | MAC address |

**Tại sao phải học?** Mọi ứng dụng web đều chạy trên stack này. Khi API chậm, lỗi `ERR_CONNECTION_REFUSED`, hay certificate hết hạn — bạn cần biết lỗi nằm ở layer nào.

## 2. TCP/IP: Nền tảng của mọi kết nối

### WHY

TCP cung cấp **reliable, ordered, connection-oriented** transport. Gần như mọi giao thức application (HTTP/1.1, HTTP/2, SSH, database) đều dựa trên TCP. Hiểu TCP giúp bạn giải thích tại sao đôi khi request bị chậm do retransmission, tại sao cần keep-alive, và tại sao UDP lại phù hợp cho video call.

### HOW

**Three-way handshake** — thiết lập kết nối:

```
Client                     Server
  | ---- SYN (seq=x) -------> |
  | <--- SYN-ACK (seq=y,ack=x+1) |
  | ---- ACK (ack=y+1) ------> |
  |        [ESTABLISHED]        |
```

**Bốn đặc điểm cần nhớ:**

| Đặc điểm | Ý nghĩa thực tế |
|----------|------------------|
| Sequence number | Đảm bảo thứ tự; mất gói sẽ retransmit |
| Flow control (window) | Tránh làm ngập receiver chậm |
| Congestion control | Tránh làm ngập network (slow start, AIMD) |
| Connection state | Tốn RAM; DDoS SYN flood khai thác điều này |

**Kiểm tra kết nối bằng CLI:**

```bash
# Linux: xem trạng thái kết nối TCP
ss -tan

# Gửi request và xem chi tiết timing
curl -v https://example.com

# Kiểm tra port có mở không (không cần telnet)
nc -zv example.com 443
```

**UDP** ngược lại: không handshake, không đảm bảo — nhẹ và nhanh, dùng cho DNS query, QUIC (HTTP/3), game, streaming.

> **Lưu ý version-specific:** HTTP/3 dùng QUIC trên UDP — đây là ngoại lệ lớn so với mô hình "HTTP luôn chạy trên TCP" truyền thống.

## 3. DNS: Hệ thống phân giải tên miền

### WHY

Con người nhớ tên (`api.github.com`), máy tính cần IP (`140.82.112.6`). DNS là "danh bạ" phân tán của Internet. Hiểu DNS giúp bạn debug lỗi "site không vào được nhưng ping IP vẫn được", cấu hình CDN, và giải thích TTL ảnh hưởng đến việc deploy như thế nào.

### HOW

**Quá trình phân giải (recursive resolution):**

```
Client → Stub Resolver (OS) → Recursive Resolver (ISP/8.8.8.8)
                                    ↓
                          Root Server (.) → TLD (.com) → Authoritative (github.com)
```

**Các loại record quan trọng:**

| Record | Mục đích | Ví dụ |
|--------|----------|-------|
| A | IPv4 | `example.com → 93.184.216.34` |
| AAAA | IPv6 | `example.com → 2606:2800:...` |
| CNAME | Alias | `www → example.com` |
| MX | Mail server | `mail.example.com` |
| TXT | Text (SPF, verify) | `v=spf1 ...` |
| NS | Name server | `ns1.example.com` |

**Caching & TTL:** Resolver cache theo TTL. Nếu TTL = 3600, thay đổi DNS mất tới 1 giờ mới lan truyền. Đây là lý do khi deploy cần giảm TTL trước.

**Debug bằng `dig`:**

```bash
dig example.com A +short
dig @8.8.8.8 example.com MX
dig +trace example.com   # xem toàn bộ chuỗi phân giải
```

> Trên Windows dùng `nslookup`. Trên macOS/Linux, `dig` (gói bind-utils) là chuẩn.

## 4. HTTP: Giao thức ứng dụng

### WHY

HTTP là "ngôn ngữ" giữa client và server. Hiểu HTTP/1.1 vs HTTP/2 vs HTTP/3, status code, header, caching giúp bạn thiết kế API đúng, tối ưu tải trang, và trả lời câu hỏi kiểu "tại sao cần HTTP/2".

### HOW

**Cấu trúc request/response:**

```http
GET /api/users HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

[body]
```

**Status code cần nhớ:**

| Nhóm | Ý nghĩa | Ví dụ |
|------|---------|-------|
| 2xx | Thành công | 200, 201, 204 |
| 3xx | Redirect | 301 (permanent), 304 (not modified) |
| 4xx | Client error | 400, 401, 403, 404, 429 |
| 5xx | Server error | 500, 502 (bad gateway), 503, 504 (timeout) |

**So sánh các phiên bản:**

| Version | Transport | Đặc điểm |
|---------|-----------|----------|
| HTTP/1.1 | TCP | Mỗi request một connection (hoặc keep-alive tuần tự), head-of-line blocking |
| HTTP/2 | TCP | Multiplexing, header compression (HPACK), binary |
| HTTP/3 | QUIC (UDP) | Giảm handshake, tránh TCP head-of-line |

**Caching headers:** `Cache-Control`, `ETag`, `Last-Modified`. Hiểu `304 Not Modified` giúp giảm băng thông.

**Thực hành với curl:**

```bash
curl -I https://example.com              # chỉ xem header
curl -X POST -H "Content-Type: application/json" -d '{"a":1}' https://api.example.com
curl --http2 -v https://example.com      # kiểm tra HTTP/2
```

## 5. TLS: Bảo mật trên đường truyền

### WHY

TLS (tiền thân là SSL) mã hóa dữ liệu giữa client và server, đảm bảo **confidentiality, integrity, authentication**. HTTPS = HTTP over TLS. Nếu không có TLS, mọi dữ liệu (mật khẩu, token) có thể bị đọc trên đường truyền. TLS cũng là nền tảng của certificate, mà developer thường xuyên phải debug (lỗi "certificate expired", "self-signed").

### HOW

**TLS 1.2 vs 1.3 — handshake:**

- **TLS 1.2**: 2 round-trip (client hello → server hello + cert → key exchange → finished).
- **TLS 1.3**: 1 round-trip, loại bỏ cipher yếu (RSA key exchange, CBC), hỗ trợ 0-RTT resumption. **Nên dùng TLS 1.3** nếu hạ tầng cho phép.

**Các thành phần:**

1. **Certificate**: chứng minh server sở hữu domain, được ký bởi CA (Certificate Authority).
2. **Handshake**: thỏa thuận cipher suite, trao đổi key (ECDHE).
3. **Session key**: khóa đối xứng dùng để mã hóa dữ liệu (nhanh hơn asymmetric).

**Kiểm tra certificate:**

```bash
# Xem cert của một domain
openssl s_client -connect example.com:443 -servername example.com

# Xem ngày hết hạn
openssl s_client -connect example.com:443 </dev/null 2>/dev/null | openssl x509 -noout -dates
```

> **Lưu ý:** `openssl s_client` cần gõ `-servername` để gửi SNI — nếu không, server có thể trả cert mặc định sai.

**Best practices:** dùng HSTS, redirect HTTP→HTTPS, tự động gia hạn cert (Let's Encrypt + certbot), cấu hình cipher suite an toàn.

1. **TCP và UDP khác nhau thế nào?** — Gợi ý: reliable/ordered vs best-effort, khi nào chọn cái nào (DNS, video, HTTP/3).
2. **Mô tả three-way handshake. Tại sao cần 3 bước?** — Gợi ý: đồng bộ sequence number hai chiều, tránh kết nối cũ.
3. **DNS resolution diễn ra như thế nào?** — Gợi ý: stub → recursive → root → TLD → authoritative; caching & TTL.
4. **Sự khác biệt giữa HTTP/1.1, HTTP/2, HTTP/3?** — Gợi ý: head-of-line blocking, multiplexing, transport layer.
5. **TLS handshake làm gì? Tại sao cần certificate?** — Gợi ý: authentication, key exchange, encryption; CA và chain of trust.
6. **Khi gõ URL, chuyện gì xảy ra từ lúc gõ đến khi thấy trang?** — Gợi ý: DNS → TCP → TLS → HTTP → render; cache ở mỗi bước.
7. **Làm sao debug một trang web không load được?** — Gợi ý: `curl -v`, `dig`, `ping`, `traceroute`, kiểm tra status code và cert.
8. **Tại sao cần HTTPS? Nếu bị MITM thì sao?** — Gợi ý: mã hóa, integrity, chống đọc/sửa; HSTS, certificate pinning.

**Bước 1 (15 phút): Khám phá DNS**
- Dùng `dig +trace example.com` để xem chuỗi phân giải từ root.

**Bước 2 (20 phút): Phân tích TCP handshake**
- Chạy `curl -v https://example.com` và đọc phần `* Trying ...` và `* Connected to ...`.
- Dùng `ss -tan` trên Linux (hoặc `netstat -an` trên Windows) để xem trạng thái kết nối.
- (Tùy chọn) Cài Wireshark (miễn phí) và bắt gói tin của một request HTTP không mã hóa (ví dụ `http://neverssl.com`) để thấy TCP handshake và HTTP header.

**Bước 3 (20 phút): HTTP & TLS inspection**
- Dùng `curl -I https://example.com` xem header.
- Dùng `openssl s_client -connect example.com:443 -servername example.com` và quan sát certificate chain, cipher, phiên bản TLS.
- So sánh với `curl --http2 -v https://example.com` để thấy HTTP/2.

**Bước 4 (20 phút): Mô phỏng lỗi và debug**
- Thử `curl -v https://expired.badssl.com` — quan sát lỗi certificate.
- Thử `curl -v https://self-signed.badssl.com` — quan sát lỗi self-signed.
- Dùng `nc -zv example.com 443` và `nc -zv example.com 80` — so sánh.

**Bước 5 (tùy chọn, 15 phút): Viết script nhỏ**
- Viết script Bash hoặc Python (dùng `requests` + `ssl`) để kiểm tra ngày hết hạn certificate của một domain và in ra cảnh báo nếu còn < 30 ngày.

> Tất cả công cụ trên đều miễn phí: `dig`, `curl`, `openssl`, `nc` có sẵn trên Linux/macOS; trên Windows có thể dùng WSL hoặc cài Git Bash.
